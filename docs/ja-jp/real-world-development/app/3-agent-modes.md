最初は小さな機能をプロジェクトに追加しましたが、大きな変更には、より確実なプロセスが必要です。GitHub Copilot app は組織の既存のワークフローに沿って動作し、適切な方法で適切な機能を構築できるように設計されています。このレッスンから数回にわたり、一般的なエージェント駆動型の開発プロセスに沿って進めます。まず issue を使って新機能を作り、コードの妥当性と機能の動作を確かめたうえで、プロジェクトにマージします。

> [!NOTE]
> 機能開発を続ける間、同じセッションを使います。通常は作業するファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主要な概念に集中するために手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がゲームをカテゴリーや発行元で絞り込める必要があります。バックログの issue には機能が説明されていますが、カテゴリーの組み合わせ方など、コーディング前に合意が必要な詳細もあります。Plan モードでそうした判断を整理し、範囲を限定した実装を Autopilot に許可します。

## 背景

AI コーディングエージェントを開発ワークフローに取り入れても、基本は変わりません。むしろ、基本がこれまで以上に重要になります。多くの開発者は、次のような流れで作業します。

1. 実装する内容の詳細が記載された issue を開きます。
2. 構築する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションのプロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れに近い形になります。

この標準的な手順に沿うことで、AI が生成したコードが要件を満たし、手書きのコードと同じ審査を受けるようにできます。

## セッションモード

**セッションモード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更案を提示し、次の操作に進む前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。エージェントが実行する前に、計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律的に作業し、入力を待たずにコードを書き、テストを実行して、改善を繰り返します。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選び、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはすでに用意された issue なので、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョンマネージャーの設定を確認してから、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前に進め方をレビューできます。issue から開始したため、Copilot は機能リクエストをすでにコンテキストとして把握しています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、issue の受け入れ基準と計画を照らし合わせます。カテゴリーと発行元による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数のカテゴリーをどのように組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質ワークフローの完了後に PR を作成します。承認する前に計画の修正を依頼してください。後の検証に使えるよう、issue の URL と合意した説明を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認によってモードも切り替わると思い込まず、アクティブなモードを確認します。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始します。作成した計画に沿って作業を繰り返し、コードを生成してテストも実行します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポートの競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同じようにマージ前のレビューが必要です。コードをレビューし、サイトを実行して問題がないことを確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数のカテゴリーや発行元の組み合わせも含め、結果を issue と承認した追加の合意事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーがテスト対象であることを確認してください。

## 新機能を試す

コードに問題がないように見えても、実際に動くでしょうか。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きましょう。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスで開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリーを選択し、結果がそのカテゴリーに一致することを確認します。フィルターをクリアして発行元を選択し、結果がその発行元に一致することを確認します。
4. カテゴリーと発行元を組み合わせ、issue と承認済みの計画に照らし合わせて結果を確認します。複数カテゴリーに対応している場合は、合意した組み合わせの動作を検証します。
5. ゲームが見つからない組み合わせを試し、結果がない場合の表示を確認します。フィルターをクリアまたはリセットして、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトを使って、このセッションに対して起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにこのセッションを保持する

フィルター機能の PR は、まだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを引き続き使います。次はカスタム指示をフィルター機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 でそれらをまとめた PR を作成してマージします。開発サーバーを停止した後はセッションをアイドル状態にしておき、次のレッスンで同じセッションに戻ります。
